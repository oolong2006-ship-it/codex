# ملخص المرحلة 0 — صفحة واحدة

**الحالة:** منتهية ومتوقفة بانتظار الاعتماد. التفاصيل في `docs/status.md`.
**تحفظ منهجي:** كل التحقق تم عبر فهرس البحث المقيد بالنطاقات الرسمية (2026-10-26) لأن بيئة التنفيذ تمنع الجلب المباشر. أعد فتح الروابط قبل أي استخدام علني.

## أهم 5 فجوات تنافسية

| # | الفجوة | الدليل | ماذا نفعل |
|---|---|---|---|
| 1 | **التحقق بالوجه + الحيوية** معروض لدى 5 منافسين (Bayzat، Jibble، Deputy، TECFY، PassMH)، ونحن لا نقدمه | competitor-matrix: `FACE` | نراهن على ربط الجهاز الموثق بالعتاد بدلًا منه (PDPL: البيومتري حساس + DPIA). خطر: المشتري قد يعتبر الوجه حدًا أدنى ← سؤال في المقابلات |
| 2 | **السعر**: Jibble يعلن خطة مجانية، وTECFY مجانية حتى 5 موظفين | `plan` في المصفوفة | التموضع على الثقة والأدلة لا السعر؛ اختبار الاستعداد للدفع قبل البناء الكامل (A-05، R-C1) |
| 3 | **الحزمة الكاملة HR + رواتب + مُدد** لدى Jisr وZenHR وBayzat | `PAYROLL-SYNC`، `BIO-DEVICE` | لا ننافس على الرواتب؛ نصدّر لها. نبيع كطبقة ثقة فوق نظام HR الحالي (R-C2) |
| 4 | **البصمة دون اتصال** لدى Palm HR وJibble وكشك Deputy | `OFFLINE` | مؤجلة للمرحلة 4 (specs §E). خطر إن كانت المطابخ/المستودعات دون شبكة (A-13) |
| 5 | **الاستراحات والعمل الإضافي والورديات المرنة** لدى أغلب المنافسين | `BREAKS`، `OT-AUTO`، `SHIFT-ADV` | المرحلة 3. الـ MVP يكفي للتجربة بالتوازي مع النظام الحالي، لا لاستبداله |

**فرضية التميز (غير مثبتة):** لم نجد منافسًا يوثق ربط الجهاز بشهادة عتاد (App Attest/Play Integrity/Key Attestation) ولا قرارًا يحمل أدلته وأسبابه ومسار اعتراض. Jibble يذكر «device lock» — يلزم التحقق. لا تُستخدم في التسويق قبل ذلك.

## نطاق الـ MVP (المرحلة 2) — `docs/prd-mvp.md`

- **الإعداد:** عميل يدوي من المنصة؛ فروع ومواقع بسياج دائرة/مضلع بإصدارات؛ إحداثيات من العنوان المختصر عبر Fake (سبل `Blocked`) أو يدويًا.
- **الموظفون:** إضافة + استيراد CSV بتقرير أخطاء؛ تفويض بالمواقع.
- **DeviceLock:** رمز تفعيل، وربط موثق، وطلب تغيير بموافقة HR، وإيقاف، وإعادة ربط على نفس الجهاز.
- **البصمة:** حضور/انصراف فقط؛ Trust Engine (طبقات A + GeoTrust B + إشارات الخطر)؛ idempotency؛ نتيجة بسبب وإجراء تالٍ؛ «لا اتصال» دون تخزين.
- **الورديات:** قوالب ثابتة، وسماح تأخر/خروج مبكر كسياسة، وورديات ليلية، وإغلاق INCOMPLETE.
- **الاستثناءات:** موظف ← مراجع واحد (مدير فرع أو HR) ← `attendance_adjustments`.
- **الإدارة:** لوحة مدير الفرع لفروعه فقط؛ تقارير لحظية وتأخر/غياب ومعلقة؛ تصدير شهري CSV/XLSX؛ صفحة أدلة؛ سجل تدقيق؛ إقفال فترة أدنى (F15).
- **خارج النطاق:** الاستراحات، والإضافي، والموافقات المتعددة، والفوترة، والوجه، والذكاء الاصطناعي، ودون اتصال، ومُدد، وAPI عامة.

29 قصة، و30 اختبار T + F1–F17 + e2e + أداء + ميداني.

## القرارات التي تحتاج اعتمادًا

1. **D-01 الاستضافة:** Supabase **غير مؤهل** (لا منطقة سعودية — مصدر رسمي). AWS «معلن» فقط. اعتماد التحقق من GCP الدمام وOracle جدة/الرياض.
2. **D-03 تعارض البرومتات:** المرحلة 2 تشترط F15 والإقفال في المرحلة 3 ← نقترح إقفالًا أدنى في المرحلة 2.
3. **D-02 / D-04 / D-05:** تصدير عام بدل مُدد؛ مستوى موافقة واحد؛ أنواع الاستراحة معطلة بسياسة.
4. **D-07 «شؤون»:** لم نجد منصة بهذا الاسم — ما المقصود؟
5. **D-08 ADR-0001:** تأكيد React Native + Expo dev build، و`@expo/app-integrity` (alpha) خلف واجهة داخلية + وحدة أصلية صغيرة لـ DeviceCheck وKey Attestation؛ رفض Firebase App Check.
6. **D-09 / D-10:** مستشار نظامي، وإشعار خصوصية للموظف قبل الـ Pilot.
