# الأمن والامتثال — التكامل المفتوح وخصوصية البيانات وسيادتها

- **الحالة:** مسودة. تحتاج مراجعة بشرية (أمن + مستشار نظامي).
- **التاريخ:** 2026-10-26
- **المراجع الداخلية:** CLAUDE.md §3 و§5، وspecs §C–§G، وdocs/research/ksa-requirements.md (P1–P7 وH1–H7)، وdocs/risks.md (R-T7 وR-L2 وR-L3)، وADR-0001، وprompts/phase-1-foundation.md.
- **النطاق:** أسطح الهجوم الجديدة التي يفتحها «الربط بأي برنامج»، وهي API عامة، وOAuth client credentials، وWebhooks، وSCIM، وSSO، وSFTP، وموصلات HR/ERP. هذه الوثيقة **تكمّل** `docs/threat-model.md` المطلوب في المرحلة 1 لمسارات الدخول وربط الجهاز، ولا تحل محله.

> **منهج التحقق:** الجلب المباشر للمواقع ممنوع في بيئة التنفيذ (الـ proxy يرد 403). لذلك تحققنا عبر محرك البحث مقيدًا بالنطاقات الرسمية (`nca.gov.sa`، و`cdn.nca.gov.sa`، و`cst.gov.sa`، و`sdaia.gov.sa`، و`dgp.sdaia.gov.sa`)، أي أننا قرأنا **ملخصات الفهرس** لا النص الكامل. كل رقم مادة أو بند منقول بهذه الطريقة يُعامل «مؤكدًا من الفهرس»، ويُراجع على النص الكامل قبل أي التزام تعاقدي. **لا نحمل اليوم أي شهادة، ولا ندّعي الامتثال لأي إطار.**

## 1. نموذج تهديد STRIDE لأسطح التكامل

**الأصول المحمية:** أحداث البصمة وأدلتها (الموقع وشهادات الجهاز)، وبيانات الموظفين، وأسرار التكامل (مفاتيح API، وclient secrets، وأسرار webhook، ومفاتيح SFTP، وبيانات اعتماد موصلات HR/ERP التي يسلمها العميل لنا)، والعزل بين العملاء.

**حدود الثقة:**
- **TB1:** نظام العميل → API العامة/SCIM. المتصل آلة، لا إنسان.
- **TB2:** منصتنا → عناوين webhook يحددها العميل. اتصال صادر إلى الإنترنت.
- **TB3:** منصتنا ↔ أنظمة HR/ERP خارجية عبر موصل يحمل سر العميل.
- **TB4:** SFTP. ملفات تدخل وتخرج.
- **TB5:** مزوّد الهوية (IdP) لدى العميل → SSO.

### 1.2 أخطر خمسة (حسب الاحتمال × الأثر)
1. **T13/T14: تسرب بين العملاء عبر مسار التكامل.** المسارات غير التفاعلية، كالعمال والموصلات وSCIM، هي الأسهل في نسيان سياق المستأجر.
2. **T6: SSRF عبر عناوين webhook.** يكفي أن يسجل مستخدم بصلاحية `tenant_admin` عنوانًا.
3. **T12: أسرار العملاء في الموصلات.** نصبح نقطة اختراق لأنظمة HR لدى عملائنا.
4. **T1/T2: مفتاح API مسرّب بنطاق واسع.**
5. **T8/T10: تصعيد صلاحيات عبر SCIM أو SSO.**

## 2. الضوابط

| ID | الضابط | التفاصيل الملزمة |
|---|---|---|
| C1 | **نطاقات المفاتيح** | كل مفتاح API أو OAuth client له scopes صريحة، مثل `attendance:read` و`employees:write` و`reports:read`. **لا يوجد** scope `*`. عمليات DeviceLock (اعتماد تغيير جهاز، وإعادة تفعيل)، وتعديل السياسات والأدوار، **غير متاحة لأي اعتماد آلي**: تبقى لمستخدم بشري مع MFA (specs §C، وF6). المفتاح مرتبط بمستأجر واحد، واختياريًا بفروع محددة (ABAC). |
| C2 | **تخزين الأسرار** | الأسرار التي **نصدرها** (مفاتيح API، وclient secrets) تُخزن hash فقط (Argon2id أو HMAC-SHA256 بمفتاح من KMS)، ويُعرض السر مرة واحدة عند الإنشاء ببادئة قابلة للفحص (`sao_live_…`). الأسرار التي **نستلمها** (بيانات موصلات HR/ERP، ومفاتيح SFTP الخاصة) تُشفَّر بـ envelope encryption: مفتاح بيانات لكل مستأجر، مغلف بمفتاح رئيسي في KMS أو Vault **داخل المملكة**. لا أسرار في `.env` الإنتاج، ولا في السجلات، ولا في رسائل الخطأ، ولا في الطوابير (تحمل المهمة مرجعًا للسر، لا السر). |
| C3 | **التدوير والانتهاء** | مفاتيح API: انتهاء افتراضي 12 شهرًا (سياسة)، وتدوير بلا انقطاع بمفتاحين نشطين معًا خلال فترة تداخل. أسرار webhook: سرّان نشطان أثناء التدوير، ويُرسل التوقيعان معًا. رموز OAuth للوصول: ≤ 15 دقيقة. مفاتيح SFTP: مفتاح SSH عام لكل مستأجر، لا كلمات مرور. إلغاء فوري من اللوحة ينعكس خلال ≤ 60 ثانية. |
| C4 | **الحد الأدنى من الصلاحيات في SCIM والـ API** | SCIM يدير الهوية والحالة فقط. **لا يمنح** الأدوار `hr` و`tenant_admin` و`platform_admin` إلا إذا فعّل العميل ربط مجموعات صريحًا، وبعد تأكيد بشري. تعطيل الحساب عبر SCIM يُلغي الجلسات وrefresh tokens. إعادة التفعيل لا تعيد ارتباط الجهاز تلقائيًا. |
| C5 | **OAuth 2.0 client credentials** | رموز وصول قصيرة، و`aud` محدد لكل API. للمؤسسات: `private_key_jwt` (RFC 7523) بدل الأسرار المشتركة، أو mTLS-bound tokens (RFC 8705). لا refresh tokens لتدفق client credentials. |
| C6 | **معدلات الطلب والحصص** | حدود لكل مفتاح ولكل مستأجر، مثل token bucket في Redis. **مسار البصمة من الجوال معزول عن حصص التكامل**، فاستهلاك API لا يبطئ البصمة. الرد 429 مع `Retry-After`. سقف لحجم الصفحة ولعمق الترقيم، وتنبيه عند استخراج جماعي غير معتاد. |
| C7 | **توقيع Webhooks** | الترويسات `X-SAO-Signature: v1=HMAC-SHA256(secret, timestamp + "." + raw_body)`، و`X-SAO-Timestamp`، و`X-SAO-Event-Id`. نافذة القبول ±5 دقائق (سياسة). نوفر في SDK والتوثيق دالة تحقق بمقارنة ثابتة الزمن، وتوصية بأن يخزن المستقبل `event_id` لمنع التكرار. السر لكل endpoint، لا لكل مستأجر. الإرسال المتكرر يحمل نفس `event_id` بطابع زمني وتوقيع جديدين. |
| C8 | **مضاد SSRF** | `https` فقط، على المنفذ 443 أو منافذ من قائمة سماح. نحل الاسم **ونثبّت عنوان IP** للاتصال نفسه، ونرفض النطاقات الخاصة والمحجوزة (RFC 1918، و127/8، و169.254/16، و100.64/10، وIPv6 ULA وlink-local، وعناوين الميتاداتا السحابية). لا نتبع إعادة التوجيه. مهلة 10 ثوانٍ، وحد لحجم الرد. الإرسال يمر عبر **egress proxy** معزول في شبكة فرعية بلا وصول داخلي. نتحقق من ملكية العنوان بـ challenge عند التسجيل. قائمة سماح بالنطاقات اختيارية لكل مستأجر. |
| C9 | **سجل التدقيق** | كل استدعاء كتابة آلي يُسجل في `audit_logs` (append-only، specs §F) مع `actor_type = api_key | oauth_client | scim | sftp | connector` ومعرف الاعتماد، **لا السر**. كذلك يُسجل إنشاء الاعتمادات وتدويرها وإلغاؤها، وتغيير عناوين webhook، وفشل التحقق المتكرر. السجلات قابلة للتصدير للعميل (SIEM) بصيغة JSON. |
| C10 | **SSO** | OIDC مفضل، وSAML مدعوم بمكتبة مصانة. نفحص `iss` و`aud` والتوقيع والصلاحية وInResponseTo. ربط نطاق البريد بالمستأجر يتطلب **إثبات ملكية النطاق** (سجل DNS TXT). خيار «SSO إلزامي» يعطل كلمات المرور لأدوار الإدارة. MFA تُفرض من الـ IdP أو منا. |
| C11 | **العزل في مسارات التكامل** | كل اعتماد آلي يحدد `tenant_id` من **الخادم** (من سجل الاعتماد)، ولا يُقبل من الطلب. كل مهمة BullMQ تحمل `tenant_id`، والعامل يفتح اتصال DB ويضبط `app.tenant_id` قبل أي استعلام. وجود اتصال دون ضبطه = خطأ يوقف المهمة. طوابير أو مفاتيح Redis مسبوقة بالمستأجر. اختبار F8 يُمدد ليشمل كل سطح تكامل. |
| C12 | **مقاومة الإغراق** | دفعات SCIM وSFTP لها سقف حجم ومعدل. معالجتها في طابور منخفض الأولوية منفصل عن طابور قرارات البصمة. |
| C13 | **SFTP** | chroot لكل مستأجر، ومفاتيح SSH فقط، وقائمة سماح IP اختيارية. التحقق من المخطط قبل الاستيراد، وتعقيم خلايا CSV التي تبدأ بـ `= + - @`. حذف ملفات التصدير بعد مدة سياسة (افتراضي 7 أيام). ملفات التصدير تحمل checksum، واختياريًا توقيع PGP. الخادم داخل المملكة. |
| C14 | **تقليل البيانات الصادرة** | انظر 3.3. الحمولات الافتراضية لا تحمل إحداثيات خامًا ولا رموز attestation. |
| C15 | **عزل الموصلات** | الموصل يعمل في عامل منفصل بصلاحيات شبكة صادرة محصورة في نطاقات النظام المستهدف، ويفك تشفير السر في الذاكرة فقط لحظة الاستخدام. يُسجل وصوله للسر في التدقيق. |
| C16 | **mTLS اختياري للمؤسسات** | للـ API الواردة: شهادة عميل من CA يرفعها العميل، مرتبطة بالاعتماد. للـ webhooks الصادرة: نقدم شهادة عميل منا عند الطلب. خيار مدفوع أو مؤسسي، لا يحل محل HMAC/OAuth بل يضاف إليهما. |

## 3. الخصوصية بالتصميم (PDPL)

> الأساس: ksa-requirements §2 (P1–P7). نحن في الغالب **معالج** (processor) لصالح العميل صاحب العمل، وهو **المتحكم** (controller). هذا التوصيف نفسه يحتاج تأكيد المستشار، لأنه يحدد من يُخطر ومن يرد على صاحب البيانات.

### 3.1 جرد البيانات

| الفئة | الحقول | الغرض | المكان | الاحتفاظ (افتراض سياسة يضبطه العميل) | يخرج في التكاملات؟ |
|---|---|---|---|---|---|
| هوية الموظف | الاسم، والرقم الوظيفي، والجوال، والبريد، والفرع، والقسم | التعريف وإدارة الحساب | DB المملكة | مدة التوظيف + فترة يحددها العميل | نعم (SCIM/API بنطاق) |
| أحداث البصمة | النوع، ووقت الخادم، ووقت الهاتف، والقرار، وreason codes | سجل الحضور (L12) | DB المملكة، append-only | **غير مؤكد نظاميًا** (ksa §6). افتراض مقترح: مدة التوظيف + 2 سنة، **بانتظار المستشار** | نعم: القرار وreason codes فقط |
| أدلة الموقع | العينات (lat/lng/accuracy/is_mock)، والعينة المختارة، و`s`، و`a`، ونسخة السياج | إثبات قرار GeoTrust (specs §B) | DB المملكة | **أقصر من الأحداث**. مقترح: 180 يومًا للعينات الخام، ثم يبقى `s` و`a` وsiteId فقط | **لا افتراضيًا** |

قاعدة: أي حقل جديد يُضاف إلى هذا الجدول قبل الدمج، مع غرضه ومدة احتفاظه.

### 3.2 حقوق صاحب البيانات (P4)
- **العلم:** إشعار داخل التطبيق قبل أول بصمة، يذكر ما يُجمع ومتى (الموقع عند البصمة فقط)، والغرض، ومدة الحفظ أو معاييرها، والجهة المتحكمة (العميل)، وكيفية ممارسة الحقوق.
- **الوصول والنسخة:** الموظف يرى سجله وأدلته (US-28)، ويطلب تصديرًا مقروءًا (BL-17).
- **التصحيح:** عبر سجل تسوية، لا تعديل الحدث (CLAUDE.md §5.3).
- **الإتلاف:** يتعارض مع واجب حفظ السجل (L12). الحل المقترح: إتلاف الأدلة الزائدة بعد مدتها، وإبقاء الحد الأدنى للسجل. الطلب يمر على المتحكم (العميل)، ونحن ننفذ تقنيًا.
- **المهلة:** 30 يومًا كهدف تشغيلي (P6). المهلة العامة في اللائحة **غير مؤكدة**.

### 3.3 تقليل البيانات في التكاملات (قيد ثابت مقترح)
- **الافتراضي:** الحمولة الصادرة (webhook وAPI وSFTP والموصلات) تحمل `decision` و`reasons[].code` و`site_id` و`server_time` و**مرجع الدليل** `evidence_ref`، وهو رابط مصادق يعود إلى منصتنا. **لا تحمل** lat/lng ولا accuracy ولا رموز attestation ولا IP.
- **الاستثناء:** scope منفصل `evidence:location:read`. يفعّله `tenant_admin` بقرار موثق (الغرض + النظام المستلم + موقع استضافته)، ويُسجل في التدقيق، ويظهر في إشعار الموظف. **يحتاج اعتمادًا (D3).**
- التصدير الشهري (CSV/XLSX) لا يحمل إحداثيات.

### 3.4 النقل خارج المملكة (م 29، P5)
- **المبدأ:** لا نقل من جهتنا. كل مكونات المعالجة داخل المملكة (القسم 4).
- **النقل الذي يبادر به العميل:** عنوان webhook أو نظام HR خارج المملكة هو نقل يقرره العميل بصفته المتحكم. نُظهر للعميل تحذيرًا عند تسجيل عنوان يُحل إلى IP خارج المملكة (تقديري، عبر GeoIP)، ونطلب إقرارًا موثقًا. العقد (DPA) ينص على أن المسؤولية عليه.
- **إن احتجنا معالجًا فرعيًا خارجيًا:** نطبق البنود التعاقدية القياسية (SCC) من SDAIA، وتقييم مخاطر النقل وفق دليل SDAIA (فبراير 2025). يلزم التقييم في حالات منها النقل بموجب الضمانات، والنقل المستمر أو واسع النطاق لبيانات حساسة. ويُوقف النقل فورًا إذا ظهر خطر عالٍ أو تعذر إنفاذ الضمانات.
  - تقييم المخاطر: https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/RiskAssessmentGuideline%20orTransferringPersonalData/ — تحقق 2026-10-26 (فهرس)
  - لائحة نقل البيانات خارج المملكة: https://sdaia.gov.sa/Documents/RegulationonPersonalDataEN.pdf — تحقق 2026-10-26 (فهرس، **ترقيم المواد يختلف بين النسخ**)
  - SCC: https://sdaia.gov.sa/Documents/StandardContractualClausesForPersonalDataTransferEN.pdf (مذكور في ksa P5)

### 3.5 تقييم الأثر (DPIA): متى يلزم
وفق ملخص الفهرس للائحة التنفيذية (المادة 25، **الرقم يُراجع**)، يلزم تقييم أثر مكتوب في حالات منها: معالجة بيانات حساسة، و**ربط مجموعتي بيانات أو أكثر من مصادر مختلفة**، ومنتج أو خدمة يُرجح أن تسبب ضررًا جسيمًا لخصوصية صاحب البيانات. المصدر: https://sdaia.gov.sa/en/SDAIA/about/Documents/ImplementingRegulation.pdf — تحقق 2026-10-26.

**تقديرنا (يحتاج تأكيد المستشار):**
- **DPIA خفيفة للموقع قبل التجربة:** مطلوبة كإجراء احترازي (ksa §6).
- **DPIA للتكامل المفتوح:** مطلوبة على الأرجح، لأن الموصلات وSCIM تربط بياناتنا ببيانات HR من مصدر آخر، وهي حالة «الربط» أعلاه.
- **DPIA إلزامية** قبل أي بيومترية (P1)، أو قبل أي قرار آلي له أثر على الموظف خارج نطاق «النظام يقترح والإنسان يعتمد».

### 3.6 الإخطار بالتسرب
وفق ملخص الفهرس للائحة التنفيذية (المادة 24، **الرقم يُراجع**): يُخطر المتحكم الجهة المختصة خلال **72 ساعة** من علمه، ويُبلغ صاحب البيانات دون تأخير غير مبرر إذا كان الضرر محتملًا. البلاغ عبر منصة حوكمة البيانات الوطنية: https://dgp.sdaia.gov.sa/wps/portal/pdp/services/personaldatabreachnotification/ — تحقق 2026-10-26.
**التزامنا التعاقدي المقترح كمعالج:** إخطار العميل خلال ≤ 24 ساعة من التأكد، ليتمكن من الالتزام بمهلة 72 ساعة. يحتاج runbook (backlog).

### 4.2 المعالجون الفرعيون

| الفئة | الخطر | القرار المقترح |
|---|---|---|
| الخرائط (عرض خريطة رسم السياج في لوحة HR) | إرسال إحداثيات الفروع، **لا الموظفين** | مسموح بمزود خارجي لعرض البلاطات فقط. **ممنوع** إرسال إحداثيات الموظفين أو عيناتهم لأي مزود خرائط (R-L3). الحساب الجغرافي محلي (PostGIS). الخيار المفضل: مزود محلي أو بلاطات ذاتية الاستضافة |
| الرسائل (SMS وOTP) | رقم الجوال ونص الرسالة | مزود سعودي مرخص. لا بيانات حضور في نص الرسالة |
| البريد | البريد والاسم | مزود داخل المملكة إن أمكن، وإلا فبريد بلا محتوى حساس («لديك إشعار، افتح التطبيق») + SCC |
| Crash reporting وAnalytics للجوال | قد يلتقط الموقع أو المعرفات أو المحتوى | ذاتي الاستضافة داخل المملكة (Sentry self-hosted مثلًا)، أو SaaS مع **تنقية على الجهاز**: لا موقع، ولا رموز، ولا PII، وتعطيل breadcrumbs الشبكة. **لا Firebase** (متسق مع ADR-0001) |
| Apple/Google (App Attest وPlay Integrity وDeviceCheck وPush) | لا مفر منها تقنيًا | الحد الأدنى: nonce وhash فقط، ولا PII في نص الإشعار. تُذكر في قائمة المعالجين الفرعيين |
| سبل (العنوان الوطني) | عنوان الفرع فقط | داخل المملكة |

**آليات منع التسرب:** (1) سجل معالجين فرعيين عام يُخطر به العملاء قبل أي إضافة. (2) egress allowlist على مستوى الشبكة، فلا خروج من الخدمات إلا لنطاقات مسجلة. (3) فحص في CI لاعتماديات الجوال يرفض SDK تحليلات أو إعلانات غير معتمد. (4) قاعدة تنقية سجلات مركزية (redaction) للحقول `lat` و`lng` و`token` و`secret` و`authorization`.

## 8. غير مؤكد (لا يُبنى عليه التزام)

| البند | السبب |
|---|---|
| النص الكامل لـ CCC-2:2024 ومتطلبات التوطين فيه | قرأنا ملخصات الفهرس. بعضها يستند إلى CCC-1 |
| عدد ضوابط ECC-2:2024 | تعارض بين النسختين العربية والإنجليزية |
| إلزام مقدم SaaS بالتسجيل لدى CST وفئته، ومستويات تصنيف البيانات في التنظيمات | لم نقرأ دليل مقدمي الخدمة (الإصدار 5) |
| أرقام مواد اللائحة التنفيذية (24 للإخطار و25 للتقييم) | من الفهرس، وقد تختلف بين النسخ |
| هل العميل التجريبي (مطاعم) من مشغلي CNI | لا يُتوقع، لكنه غير مؤكد |
| تاريخ خبر CST عن ستة مزودين عالميين، ووجود مناطق تشغيلية فعلية لكل منهم | التاريخ لم يظهر في الفهرس، والتسجيل ليس بالضرورة منطقة جاهزة |
| مهلة الرد العامة على طلبات صاحب البيانات | ksa §6 |
