## المنتج في سطرين

**«ثَبْت — Thabt»** (اسم عمل، غير مفحوص كعلامة): **طبقة ثقة للحضور تعمل فوق أي نظام HR.** كل بصمة من هاتف موظف موثّق تصبح قرارًا يصدره الخادم ومعه أسبابه وأدلته، ويصل إلى أي نظام عبر واجهة مفتوحة — دون أجهزة إضافية ودون تتبع.

لا ننافس Jisr وZenHR وBayzat على الرواتب؛ نغذيها بحضور يمكن إثباته. ولا ننافس الخطط المجانية على السعر؛ ننافس على **الدليل**.

## كيف تعمل الأجزاء معًا

```
 هاتف الموظف (جهاز مربوط + attestation)
        │  عينات موقع عند البصمة فقط + Wi-Fi متصل (مقترح) + إشارات سلامة
        ▼
 Trust Engine على الخادم ── specs §A/§B + Evidence score قابل للتفسير
        │  القرار + reasons[] + signals[] + نسخة السياسة + نسخة السياج
        ▼
 attendance_events (append-only) ──► الجلسات ──► الاستثناءات ──► إقفال الفترة
        │
        ▼  Transactional Outbox (داخل الـ monolith)
 ┌──────────────┬──────────────┬─────────────┬───────────────┐
 REST/OpenAPI   Webhooks رفيعة  SCIM (موظفون)  ملفات CSV/XLSX/SFTP
 (scopes)       (HMAC، بلا إحداثيات) (مصدر حقيقة HR)  (+ موصلات Jisr/ZenHR/Odoo…)
```

## الركائز الخمس ← الوثيقة التي تفصّلها

## الاختبارات الإضافية المقترحة

- **F19–F3x** (trust-accuracy §8): مثل عينات متناقضة، وصلاحية موقع تقريبي، وسفر مستحيل مع هامش الدقة، ورفع Wi-Fi.
- **S1–S31** (security §6): مثل webhook بتوقيع منتهٍ، وSSRF إلى عنوان داخلي، ومفتاح بنطاق ناقص، وتسرب بين العملاء عبر الطوابير.
- **لا تُضاف إلى specs §G** إلا بالقرار PD-14.

## ما لم يُتحقق منه بعد (يجب قبل أي ادعاء)

- كل التحقق تم عبر فهرس البحث المقيد بالنطاقات الرسمية لا بفتح الصفحات (سياسة الشبكة).
- أنواع المصادقة ودلالات الكتابة في APIs: Jisr وZenHR وOdoo (`hr.attendance`)؛ وتوثيق Bayzat وPalm HR غير منشور أو غير موجود.
- سلوك `NEHotspotNetwork.fetchCurrent` في iOS بدقة (شرط واحد أم كل الشروط).
- أرقام مواد اللائحة التنفيذية لـ PDPL الخاصة بالإخطار وتقييم الأثر؛ وانطباق تصنيف CST علينا.
- أي رقم دقة أو نسبة PENDING: **فرضيات تُقاس** في الاختبار الميداني والـ Pilot، لا ادعاءات.
