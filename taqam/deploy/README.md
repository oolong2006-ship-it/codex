# دليل الإطلاق الرسمي لمنصة شؤون

هذا الدليل يشغّل منصة شؤون الحقيقية على خادم واحد: الموقع، ولوحة تحكم الشركات، وتطبيق الموظف، وبوابة مالك المنصة، والخادم (API)، وقاعدة البيانات، مع شهادة HTTPS ونسخ احتياطي يومي (ونسخة مشفّرة اختيارية خارج الخادم)، وتراجع آمن عن أي تحديث.

> جُرِّب هذا الإعداد كاملاً قبل تسليمه: بناء الصور، وتشغيل الحاويات، وتطبيق قاعدة البيانات، وHTTPS، وتسجيل شركة جديدة، وتفعيلها من البوابة، ودخول المالك، والنسخ الاحتياطي والاسترجاع، وإعادة التشغيل دون فقدان البيانات.

> **أول مرة تنشر موقعاً؟** ابدأ من [الدليل المفصّل للمبتدئين](FIRST-TIME.md): كل نقرة مشروحة.

**الوقت المتوقع:** ساعة إلى ساعتين، معظمها انتظار.
**تحتاج:** دومين، وخادم Ubuntu، وبريد رسمي (اختياري في البداية).

## الخطوة 1: جهّز ما تحتاجه

| العنصر | المواصفات | ملاحظات |
|---|---|---|
| الدومين | `shuoon.net` | من أي مزوّد دومينات |
| خادم سحابي | Ubuntu 24.04، و2–4 معالجات، و8GB ذاكرة، و80GB تخزين | انظر «أين تُستضاف البيانات؟» أدناه |
| بريد رسمي | `hello@shuoon.net` | Google Workspace أو Zoho أو Microsoft 365. لإرسال الفواتير والتذكيرات |

### أين تُستضاف البيانات؟

المنصة تحفظ رواتب وهويات وآيبانات موظفي كل الشركات العميلة. شروط المنصة تعِد بأن **«موقع الاستضافة يُذكر في العقد، والاستضافة داخل المملكة متاحة عند الطلب»**:
- **بيانات عملاء حقيقيين:** يُفضَّل خادم في **منطقة سعودية**: Google Cloud (الدمام `me-central2`)، أو Oracle Cloud (جدة/الرياض)، أو STC Cloud. الخطوات في [FIRST-TIME.md ← الخيار ب](FIRST-TIME.md#الخيار-ب-خادم-داخل-المملكة-google-cloud--الدمام).
- **DigitalOcean أو أي منطقة خارج المملكة:** للتجربة والعرض، أو لعميل وافق صراحةً في العقد على الاستضافة خارج المملكة بعد إبلاغه بموقعها.
- السكربتات نفسها تعمل على أي خادم Ubuntu 24.04، والانتقال بين خادمين يتم بنسخة احتياطية واسترجاعها.

عند إنشاء الخادم:
- اختر **Ubuntu 24.04 LTS**.
- اختر الدخول **بمفتاح SSH** (لا بكلمة مرور). إذا وُجد مفتاح في `/root/.ssh/authorized_keys` يعطّل `setup-server.sh` الدخول بكلمة المرور تلقائياً.
- **فعّل النسخ الاحتياطي من المزوّد** (DigitalOcean Backups، أو Snapshot schedule في Google Cloud): إلزامي.
- فعّل مراقبة المزوّد (DigitalOcean Monitoring) لتنبيهات القرص والذاكرة.
- افتح المنافذ **22 و80 و443** في جدار الحماية الخاص بالمزوّد إن وُجد، وثبّت **عنوان IP العام** (Static IP) وانسخه.

## الخطوة 2: اربط الدومين بالخادم (DNS)

من لوحة مزوّد الدومين، أضف ثلاثة سجلات من نوع **A**، كلها تشير إلى عنوان IP الخادم:

| النوع | الاسم (Host) | القيمة |
|---|---|---|
| A | `@` | عنوان IP الخادم |
| A | `www` | عنوان IP الخادم |
| A | `api` | عنوان IP الخادم |

انتظر من 5 دقائق إلى ساعة حتى ينتشر الربط. **تأكد من الأسماء الثلاثة كلها** قبل التشغيل، من dnschecker.org (النوع A) أو من جهازك:

```bash
nslookup shuoon.net
nslookup www.shuoon.net
nslookup api.shuoon.net
```

يجب أن يظهر عنوان خادمك للثلاثة، وإلا لن تصدر شهادة HTTPS للاسم الناقص.

## الخطوة 3: ادخل الخادم وجهّزه

من جهازك (Terminal في ماك ولينكس، أو PowerShell في ويندوز):

```bash
ssh root@عنوان_الخادم
```

ثم داخل الخادم:

```bash
# 1) نزّل الكود
git clone -b claude/great-hawking-bm4a83 https://github.com/oolong2006-ship-it/codex.git shuoon
cd shuoon/taqam

# 2) جهّز الخادم: Docker، وتدوير السجلات، والجدار الناري، وfail2ban، وذاكرة إضافية
sudo bash deploy/scripts/setup-server.sh
```

إذا طلب السكربت في نهايته إعادة التشغيل: `reboot`، ثم ادخل مجدداً و`cd shuoon/taqam`.

> **الفرع:** الأمر أعلاه يستخدم فرع التطوير الحالي. لاحقاً سيُجهَّز فرع إصدارات مستقر؛ عندها اكتب اسمه في `DEPLOY_BRANCH` داخل `deploy/.env` فيسحب `deploy.sh` منه فقط.

> **إذا كان المستودع خاصاً (Private):** أنشئ رمز وصول للقراءة فقط من GitHub ← Settings ← Developer settings ← Fine-grained tokens، بصلاحية Contents: Read على مستودع codex. ثم استخدم:
> `git clone -b claude/great-hawking-bm4a83 https://<الرمز>@github.com/oolong2006-ship-it/codex.git shuoon`

## الخطوة 4: أنشئ ملف الإعدادات

```bash
bash deploy/scripts/init-env.sh
```

سيسألك عن:
- **الدومين:** اكتب `shuoon.net`.
- **بريد شهادات HTTPS:** اضغط Enter لاعتماد `hello@shuoon.net`.
- **بريد دخولك كمالك للمنصة**، و**كلمة مرور قوية** من 12 حرفاً على الأقل (مرتين للتأكيد، وبدون علامة `'`).

يولّد السكربت تلقائياً كلمة مرور قاعدة البيانات ومفتاح التشفير، ويحفظها في `deploy/.env` بصلاحيات مقفلة (600).

> **قاعدة الكتابة في `deploy/.env`:** كل قيمة بين علامتي تنصيص مفردتين، مثل `SMTP_PASS='abc$12 #x'`. بدونهما يحذف Docker ما بعد ` #` ويستبدل ما بعد `$`، فتتغيّر كلمة المرور بصمت. القيمة نفسها لا يجوز أن تحتوي `'`.

> **كلمة مرور مالك المنصة:** تُستخدم القيمة في `.env` لإنشاء حسابك عند أول تشغيل. يُنصح بتغييرها من البوابة بعد أول دخول. لإعادة تعيينها لاحقاً (إذا نسيتها) ضع قيمة جديدة في `PLATFORM_ADMIN_PASSWORD` ثم `bash deploy/scripts/deploy.sh --no-pull`: تُطبَّق الجديدة وتُلغى جلسات الدخول القائمة.

**إعداد البريد الصادر (اختياري الآن):** افتح الملف وعبّئ إعدادات SMTP من مزوّد بريدك (القيم بين `'...'`، خصوصاً `SMTP_PASS`):

```bash
nano deploy/.env
```

| المزوّد | SMTP_HOST | SMTP_PORT | SMTP_USER / SMTP_PASS |
|---|---|---|---|
| Google Workspace | `smtp.gmail.com` | 587 | بريدك + **كلمة مرور تطبيق** (App Password) |
| Zoho Mail | `smtp.zoho.sa` (أو `smtp.zoho.com`) | 587 | بريدك + كلمة المرور أو كلمة مرور تطبيق |
| Microsoft 365 | `smtp.office365.com` | 587 | بريدك + كلمة المرور |

بدون SMTP تعمل المنصة طبيعياً، لكن الفواتير والتذكيرات تُحفظ في «الرسائل» ببوابتك دون إرسال.

## الخطوة 5: شغّل المنصة

```bash
bash deploy/scripts/deploy.sh --no-pull
```

أول تشغيل يستغرق من 5 إلى 10 دقائق لبناء الواجهة والخادم، والتشغيلات اللاحقة أسرع. بعدها افحص:

```bash
bash deploy/scripts/check.sh
```

يجب أن ترى ✓ أمام الخادم والموقع وصفحة الدخول، وتفاصيل شهادة HTTPS من Let's Encrypt. إذا استمرت ✗ أكثر من 10 دقائق: تأكد من سجلات DNS الثلاثة، ثم اعرض سجل الشهادات:

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs --tail 50 caddy
```

## الخطوة 6: جرّب المنصة الحقيقية

1. افتح `https://www.shuoon.net`. يجب أن يظهر القفل 🔒 في المتصفح.
2. ادخل من `https://www.shuoon.net/login` ببريد وكلمة مرور مالك المنصة، فتنتقل إلى بوابتك `/admin`.
3. من «الإعدادات» في البوابة: راجع أسعار الباقات، ومدة التجربة، و**بيانات الفوترة** (اسم منشأتك، والرقم الضريبي، والسجل التجاري، والآيبان)، و**التذكيرات**.
4. سجّل شركة تجريبية من `https://www.shuoon.net/signup`، ثم فعّلها من البوابة، وادخل بحسابها.
5. احذف الشركة التجريبية من البوابة بعد التجربة.

🎉 المنصة جاهزة. أكمل في نفس اليوم **المراقبة** و**النسخ خارج الخادم** (أدناه).

## الخطوة 7: المراقبة

| ماذا | كيف |
|---|---|
| هل المنصة تعمل؟ | مراقب مجاني في **UptimeRobot** (أو مثله) على `https://api.shuoon.net/api/health` (يفحص الخادم وقاعدة البيانات) وعلى `https://www.shuoon.net`، كل 5 دقائق، بتنبيه على بريدك |
| القرص والذاكرة | DigitalOcean ← Monitoring ← Create Alert Policy: القرص > 80%، والذاكرة > 90%، والمعالج > 90% |
| هل النسخ اليومي يعمل؟ | فحص في **healthchecks.io** (Period يوم، Grace ساعتان)، وضع رابطه في `BACKUP_HEARTBEAT_URL` داخل `deploy/.env`. يُطلب الرابط بعد كل نسخة ناجحة، و`/fail` عند الفشل (فشل pg_dump، أو مساحة غير كافية، أو فشل الرفع الخارجي) |

بعد تعديل `.env`: `bash deploy/scripts/deploy.sh --no-pull` ثم `bash deploy/scripts/backup-test.sh`.

## الخطوة 8: نسخة مشفّرة خارج الخادم (يُنصح بها بشدة)

اختيارية تماماً: بدون هذه القيم يبقى النسخ محلياً كما هو. عند تعبئتها تُشفَّر كل نسخة يومية بـ GPG (AES-256) بعبارة سر من عندك، وتُرفع بـ rclone إلى أي تخزين متوافق مع S3 (DigitalOcean Spaces، أو Google Cloud Storage بمفاتيح HMAC، أو Oracle Object Storage…)، وتُحذف هناك بعد `OFFSITE_KEEP_DAYS` يوماً.

```
OFFSITE_S3_ENDPOINT='fra1.digitaloceanspaces.com'
OFFSITE_S3_REGION='fra1'
OFFSITE_S3_BUCKET='shuoon-backups-2026'
OFFSITE_S3_ACCESS_KEY='...'
OFFSITE_S3_SECRET_KEY='...'
BACKUP_ENCRYPTION_PASSPHRASE='...'   # openssl rand -base64 30 — 20 حرفاً على الأقل
```

- **احفظ عبارة التشفير والمفاتيح في مدير كلمات مرور خارج الخادم.** بدون العبارة لا يمكن فك أي نسخة.
- أنشئ مفتاح Spaces بصلاحية **Limited Access** على هذا الـ bucket فقط.
- إذا كان الخادم داخل المملكة، فاختر تخزيناً داخل المملكة أيضاً.
- الأدوات (rclone وgnupg وcurl) مثبّتة في صورة `backup` الصغيرة (`deploy/backup/Dockerfile`، مبنية على `postgres:16-alpine`) تُبنى مرة مع `deploy.sh`، فلا تحتاج الحاوية الإنترنت عند إعادة تشغيلها.
- إذا فشل الرفع تبقى النسخة المحلية، ويُعاد الرفع كل 10 دقائق، ويُرسل `/fail` إلى رابط النبض.

| أريد | الأمر |
|---|---|
| تجربة الإعداد الآن | `bash deploy/scripts/backup-test.sh` |
| عرض النسخ الخارجية | `bash deploy/scripts/offsite.sh list` |
| تنزيل نسخة وفك تشفيرها إلى `deploy/backups` | `bash deploy/scripts/offsite.sh get shuoon-2026-11-01-0300.dump.gpg` |
| فك نسخة يدوياً على جهازك (خادم ضائع) | `gpg --decrypt -o x.dump shuoon-….dump.gpg` (Gpg4win في ويندوز، GPG Suite في ماك) ثم `restore.sh` على الخادم الجديد |

## العمليات اليومية

| أريد أن… | الأمر (من مجلد `shuoon/taqam`) |
|---|---|
| أحدّث المنصة لآخر نسخة | `bash deploy/scripts/deploy.sh` |
| أتراجع عن آخر تحديث | `bash deploy/scripts/rollback.sh` (انظر «التحديث والتراجع») |
| أفحص أن كل شيء يعمل | `bash deploy/scripts/check.sh` |
| آخذ نسخة احتياطية الآن | `bash deploy/scripts/backup-now.sh` |
| أسترجع نسخة احتياطية | `bash deploy/scripts/restore.sh deploy/backups/<الملف>.dump` |
| أتراجع عن آخر استرجاع | `bash deploy/scripts/restore.sh --undo` |
| أجرّب النسخ التلقائي الآن | `bash deploy/scripts/backup-test.sh` |
| أشاهد سجل الخادم | `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f api` |
| أعيد تشغيل الخادم فقط | `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env restart api` |
| أغيّر كلمة مرور مالك المنصة | من البوابة. وإذا نسيتها: قيمة جديدة في `PLATFORM_ADMIN_PASSWORD` (بين `'...'`) ثم `bash deploy/scripts/deploy.sh --no-pull` — تُلغى الجلسات القائمة |
| أضيف مديراً آخر للبوابة | من البوابة: الإعدادات ← مديرو المنصة |

**النسخ الاحتياطي:**
- يعمل تلقائياً كل يوم الساعة 3 فجراً بتوقيت الرياض، وتُحفظ النسخ في `deploy/backups` (صلاحيات root فقط) لمدة `BACKUP_KEEP_DAYS` يوماً (14 افتراضياً). تُحذف القديمة فقط بعد نسخة ناجحة.
- إذا كانت المساحة الحرة أقل من ضعف حجم آخر نسخة، تُتخطّى النسخة ويُرسل تنبيه `/fail` إلى رابط النبض.
- النسخة خارج الخادم: الخطوة 8. أو يدوياً من جهازك: `scp -r root@عنوان_الخادم:~/shuoon/taqam/deploy/backups ./shuoon-backups` (احفظها مشفّرة: فيها رواتب وآيبانات كل العملاء).

**الاسترجاع (`restore.sh`) آمن:**
1. يفحص الملف، ويأخذ نسخة `before-restore` من الوضع الحالي.
2. يسترجع النسخة في قاعدة مؤقتة جديدة `shuoon_restore` في **معاملة واحدة** (`--single-transaction --exit-on-error`) والمنصة ما زالت تعمل. إذا فشل أي شيء تُحذف المؤقتة ولا يتغيّر شيء.
3. يوقف الخادم ثوانيَ، ويبدّل الأسماء: الحالية ← `shuoon_old_<التاريخ>`، والمسترجَعة ← `shuoon`، ثم يعيد تشغيل الخادم مهما حدث.
4. **نسخة من إصدار أقدم:** لأنها تُسترجع في قاعدة فارغة تماماً، تعود كما كانت بجدول تحديثاتها، ثم يطبّق الخادم عند تشغيله التحديثات الأحدث تلقائياً (`prisma migrate deploy`). لا تبقى جداول من الإصدار الجديد مختلطة بها.
5. تبقى القاعدة القديمة للتراجع (`restore.sh --undo`) حتى الاسترجاع التالي. يحتاج ذلك مساحة تساوي حجم القاعدة مرة إضافية.

## التحديث والتراجع

`deploy.sh` في كل تحديث:
1. يسحب الفرع `DEPLOY_BRANCH` من `deploy/.env` (فارغ = الفرع الحالي) بـ fast-forward فقط. إذا فشل السحب يشرح السبب والحل بالعربية ولا يمس المنصة.
2. يأخذ نسخة `pre-deploy` من قاعدة البيانات (ويتوقف إذا فشلت).
3. يحفظ الصور الحالية باسم `shuoon-api:prev` و`shuoon-web:prev` و`shuoon-backup:prev`.
4. يحدّث الصور الجاهزة (postgres وcaddy) ويبني الجديدة على أحدث صور الأساس (`--pull`). إذا فشل البناء تبقى المنصة القديمة تعمل.
5. يشغّل، ثم ينظّف الصور غير المستخدمة وذاكرة البناء الأقدم من أسبوع.

**إذا ظهرت مشكلة بعد التحديث:**

```bash
bash deploy/scripts/rollback.sh                # النسخة السابقة + البيانات كما كانت قبل التحديث
bash deploy/scripts/rollback.sh --images-only  # النسخة السابقة مع إبقاء البيانات الحالية
```

- الوضع الافتراضي يسترجع نسخة `pre-deploy` (عبر `restore.sh`)، فيُفقد ما أُدخل بعد التحديث، لكن القاعدة الحالية تبقى محفوظة وتُعاد بـ `restore.sh --undo`.
- `--images-only` فقط إذا كان التحديث لا يغيّر قاعدة البيانات (اسأل المطوّر).
- بعد التراجع **لا تشغّل `deploy.sh`** حتى يُصلَح الخلل في GitHub، وإلا يُبنى التحديث نفسه من جديد.

## ما الذي يعمل على الخادم؟

| الحاوية | الدور |
|---|---|
| `caddy` | يستقبل الزوار على 80 و443، ويصدر شهادات HTTPS ويجددها تلقائياً، ويحوّل `shuoon.net` إلى `www` |
| `web` | الموقع ولوحة التحكم وتطبيق الموظف وبوابة المنصة على `www.shuoon.net` |
| `api` | الخادم على `api.shuoon.net`. يطبّق تحديثات قاعدة البيانات تلقائياً عند كل تشغيل، ويرسل التذكيرات يومياً الساعة 9 صباحاً |
| `db` | قاعدة بيانات PostgreSQL 16 غير مكشوفة للإنترنت |
| `backup` | النسخ الاحتياطي اليومي، والنسخة المشفّرة خارج الخادم ورابط النبض (اختياريان) |

سجلات كل الحاويات تُدوَّر تلقائياً (5 ملفات × 20MB): في `/etc/docker/daemon.json` الذي يكتبه `setup-server.sh`، وفي ملف compose نفسه. الحاويتان `api` و`web` تعملان بمستخدم غير root (`node`).

## حل المشكلات

| المشكلة | الحل |
|---|---|
| المتصفح يقول الشهادة غير صالحة | تأكد أن سجلات DNS الثلاثة تشير لعنوان الخادم وأن المنفذين 80 و443 مفتوحان، ثم: `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs caddy` |
| `check.sh` يُظهر ✗ للخادم | `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs api`، وغالباً قيمة ناقصة في `deploy/.env` |
| لا أستطيع الدخول بكلمة مرور مالك المنصة | تأكد أن القيمة في `.env` بين `'...'`. ثم ضع قيمة جديدة و`deploy.sh --no-pull` |
| `deploy.sh` يقول «تعذّر تحديث الكود» | اتبع الحلول التي يطبعها (تعديلات محلية، أو فرع أُعيدت كتابته، أو اسم فرع خاطئ في `DEPLOY_BRANCH`) |
| تحديث سبّب مشكلة | `bash deploy/scripts/rollback.sh` |
| تنبيه «النسخ» من healthchecks.io | `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs --tail 50 backup` |
| توقف البناء بسبب الذاكرة | تأكد أن `setup-server.sh` أنشأ ملف swap: `swapon --show` |
| لا تصل رسائل البريد | راجع «الرسائل» في البوابة: الحالة FAILED تعرض سبب الخطأ. تأكد من إعدادات SMTP، ومن «كلمة مرور التطبيق» في Google |
| نسيت كلمة مرور مالك المنصة | قيمة جديدة في `PLATFORM_ADMIN_PASSWORD` داخل `deploy/.env` ثم `bash deploy/scripts/deploy.sh --no-pull` (تُلغى الجلسات القائمة) |

## قبل الإطلاق التجاري

- [ ] سجل تجاري، والتسجيل في ضريبة القيمة المضافة إن لزم، وتعبئة بيانات الفوترة في إعدادات البوابة.
- [ ] الفوترة الإلكترونية (منصة فاتورة من هيئة الزكاة): الفواتير الحالية فواتير ضريبية للطباعة، وليست مربوطة بالهيئة بعد.
- [ ] مراجعة قانونية لسياسة الخصوصية والشروط وفق نظام حماية البيانات الشخصية.
- [ ] فحص العلامة التجارية «شؤون» وتسجيلها.
- [ ] نسخ احتياطي خارج الخادم مفعّل ومجرَّب (الخطوة 8)، ونسخ المزوّد (Backups/Snapshots) مفعّل.
- [ ] المراقبة مفعّلة (الخطوة 7).
- [ ] موقع الاستضافة مكتوب في عقد كل عميل، وخادم داخل المملكة لمن يطلب ذلك.
- [ ] النشر من فرع إصدارات مستقر (`DEPLOY_BRANCH`) لا من فرع تطوير.
